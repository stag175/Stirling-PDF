# Desktop (Tauri) OAuth2 callback — security audit

> Roadmap item **D1**. The proprietary security config disables Spring's CSRF filter and runs the
> main chain **stateless**, while the desktop (Tauri) OAuth2 flow carries a custom `state` and a
> client-supplied `nonce`. This audit answers the roadmap's question — *can the nonce/state be
> swapped on the desktop `window.location` redirect path?* — and records the residual hardening items.
>
> **Read-only analysis. No code was changed.** Every claim cites the source.
>
> **Scope:** `oauth2/TauriAuthorizationRequestResolver.java`, `oauth2/TauriOAuthUtils.java`,
> `oauth2/CustomOAuth2AuthenticationSuccessHandler.java`,
> `configuration/SecurityConfiguration.java`. (The SAML desktop path is analogous but out of scope;
> a separate context-path double-prefix bug in the SAML error redirect was already flagged elsewhere.)

## The flow (grounded)

1. The desktop app opens the system browser at
   `/oauth2/authorization/{provider}?tauri=1&nonce=<desktop-nonce>`.
2. `TauriAuthorizationRequestResolver.customize` takes the `OAuth2AuthorizationRequest` built by
   Spring's `DefaultOAuth2AuthorizationRequestResolver` — **which already generated a cryptographically
   random `state`** — and, only when `tauri=1`, rewrites the state to
   `tauri:<original-random-state>[:<nonce>]` (lines 44–56). The original random state is **preserved,
   not replaced**; the marker and nonce are *wrapped around* it.
3. Spring persists that `OAuth2AuthorizationRequest` (state included) via the **default
   `HttpSessionOAuth2AuthorizationRequestRepository`** — no custom repository bean exists — i.e. in a
   transient `HttpSession`.
4. The provider redirects to `/login/oauth2/code/{provider}?code=…&state=tauri:<rand>[:<nonce>]`.
5. Spring's `OAuth2LoginAuthenticationFilter` **compares the returned `state` against the
   session-stored authorization request**. Mismatch ⇒ authentication fails *before* any success
   handler runs.
6. `CustomOAuth2AuthenticationSuccessHandler` issues a JWT and redirects the browser to
   `origin + redirectPath + "#access_token=" + jwt [+ "&nonce=" + nonce]` (lines 214–238), where the
   nonce is re-extracted from the validated state by `TauriOAuthUtils.extractNonceFromState`.
7. The desktop callback page reads the fragment and verifies the `nonce` equals the one it generated.

## Primary finding — nonce/state swap is **prevented**

**The disabled `http.csrf()` (SecurityConfiguration line 264) does _not_ disable OAuth2 `state`
validation.** These are two different mechanisms: `CsrfConfigurer::disable` removes the
`CsrfFilter` used for form/API CSRF tokens, whereas the OAuth2 authorization-code `state` check is
performed by `OAuth2LoginAuthenticationFilter` against the authorization-request repository. The
latter is still active.

Consequences:

- **State cannot be swapped.** The random `state` is generated by Spring, stored in the caller's
  session, and must match on callback. An attacker has neither the victim's session nor the random
  value, so a forged/substituted `state` is rejected at step 5.
- **Nonce cannot be swapped independently.** The nonce is embedded *inside* the state
  (`tauri:<rand>:<nonce>`), so it is covered by the same integrity check — changing the nonce changes
  the state, which then fails validation. An attacker running their own flow gets their own
  `(state, nonce)` pair and cannot inject their token into a victim's desktop, because the desktop
  verifies the nonce it itself generated.
- **The Tauri resolver does not weaken the state.** It only prepends `tauri:` and appends `:<nonce>`
  (and short-circuits if the state is null or already prefixed), preserving the random entropy.

**Token delivery is via the URL fragment (`#access_token=…`), not the query string** — the better
choice: fragments are not sent to servers, not written to access logs, and not forwarded in the
`Referer` to a cross-origin navigation.

**Verdict: the desktop OAuth2 nonce/state cannot be swapped on the redirect path.** The roadmap's
"high risk if wrong" concern does not materialise here.

## Residual hardening items (the redirect *origin*, not the nonce/state)

The genuinely interesting surface is **how the redirect `origin` is chosen**
(`buildContextAwareRedirectUrl` → `resolveForwardedOrigin` → `resolveOriginFromReferer` →
`buildOriginFromRequest`), because that origin is where the `#access_token` is delivered. None of the
below is exploitable by a pure web attacker in a correctly-configured reverse-proxy deployment (a
browser cannot set `X-Forwarded-*`/`Referer` on the victim's IdP→callback navigation, and the
callback path for the Tauri flow is the fixed `/auth/callback/tauri`), but each is worth tightening:

1. **`X-Forwarded-Host` is trusted first (lines 251–276).** If a deployment terminates the app
   directly, or a proxy passes through *client-supplied* `X-Forwarded-Host`, the redirect origin (and
   thus the token destination) is attacker-influenceable via host-header injection. *Mitigation:* have
   the proxy authoritatively set/overwrite `X-Forwarded-*`, and/or pin an **allow-list of trusted app
   origins** server-side instead of trusting headers.

2. **`isOAuthProviderDomain` is a hardcoded, incomplete allow-list** (Google/GitHub/Microsoft/
   LinkedIn/Apple — lines 350–358). For any other IdP (Keycloak, Okta, Auth0, ADFS — note the ADFS
   deployment referenced in the D2 work), the `Referer`-based origin fallback is **not** excluded, so
   when `X-Forwarded-Host` is absent the origin can resolve to the **IdP's** domain → broken desktop
   login and an `#access_token` fragment navigated to the IdP origin. *Mitigation:* prefer a single
   server-configured canonical app origin over `Referer` heuristics.

3. **Stateless chain + session-backed authorization-request repository.** The main chain is
   `SessionCreationPolicy.STATELESS` (SecurityConfiguration line 245), yet OAuth2 `state` relies on a
   transient `HttpSession` created by the default repository. In multi-instance deployments without
   sticky sessions or a shared session store, the callback may not find the stored request → login
   fails, and the state-CSRF guarantee depends on that session surviving. *Mitigation:* use a
   cookie-based (signed/encrypted) `AuthorizationRequestRepository` for true statelessness, or ensure
   session affinity. (Relates to the cluster-backplane workstream.)

4. **Minor:** `extractNonceFromState` splits on `:` and takes the last segment (TauriOAuthUtils
   lines 33–37). Safe today because Spring's state is URL-safe Base64 (no `:`); a desktop client that
   put a `:` in its nonce would see it truncated. Worth a documented constraint on the nonce charset.

## Recommendation

The nonce/state integrity is sound; **the actionable follow-up is to make the redirect-origin
derivation deterministic** (server-configured canonical origin / trusted-origin allow-list) rather
than inferring it from `X-Forwarded-Host`/`Referer`. That removes items 1–2 and is a contained,
testable change — spawned as a separate task.
